## 摘要
语音智能体正在汇聚到一种协作模式：全双工交互模型作为对话入口保持在实时信道上，而搜索、推理和编码则通过异步委派处理。双工模型支持持续听说，但复杂推理和工具使用可能超出其能力。编码智能体可以规划和执行较长任务，但其串行接口不太适合实时对话。将它们结合需要一个协调框架，在保持对话响应的同时协调任务接受、进度、取消、替换和结果交付。现有协调框架往往依赖耦合的启发式规则，难以根据证据进行系统性改进。我们提出了 DuplexAgent，一个全双工协作系统，其协调框架将该工作流表示为六个可编辑模块；以及 Duplex-Harness-RSI，一个根据交互轨迹修订这些模块的闭环。模拟器自动生成带时间约束的测试对话、运行系统，并生成失败轨迹，以识别需要修复的协作模块。委派池中的推理大语言模型和编码智能体也为改进闭环服务：测试规划器根据观察到的弱点和修复档案选择下一组测试，框架编辑器提出有针对性的模块修改。因此，服务于用户的能力也能改进系统自身的协调。在智能、智能体和双工基准上的实验表明，DuplexAgent 将连续交互与困难推理和复杂任务执行结合起来，在口语知识和可执行工具得分上优于所比较的委派系统，同时保持较强的打断响应。协调框架消融进一步显示，这种模块化、可验证的闭环优于初始框架以及缺乏诊断与修复档案的反复编辑。

## Abstract
Voice agents are converging on a collaboration pattern: a full-duplex interaction model stays on the live channel as the entry to the conversation, while search, reasoning, and coding are handled through asynchronous delegation. A duplex model supports continuous listening and speaking, but complex reasoning and tool use may exceed its capabilities. A coding agent can plan and execute extended tasks, but its sequential interface is a poor fit for live conversation. Combining them requires a harness that coordinates task acceptance, progress, cancellation, replacement, and result delivery while keeping the conversation responsive. Existing harnesses often rely on coupled heuristics, making them difficult to improve systematically from evidence. We present DuplexAgent, a full-duplex collaboration system whose harness expresses this workflow as six editable modules, and Duplex-Harness-RSI, a closed loop that revises them from interaction traces. A simulator automatically generates timed test conversations, runs the system, and produces failure traces that identify the collaboration modules requiring repair. Reasoning LLMs and coding agents in the delegation pool also serve the improvement loop: the Exam Planner selects the next tests from observed weaknesses and the repair archive, and the Harness Editor proposes targeted module changes. The capabilities that serve the user thus also improve the system's coordination. Experiments on intelligence, agentic, and duplex benchmarks show that DuplexAgent combines continuous interaction with difficult reasoning and complex task execution, achieving stronger spoken-knowledge and executable-tool scores than the compared delegated systems while maintaining strong interruption response. A harness ablation further shows that this modular, verifiable loop outperforms the initial harness and repeated editing that lacks its diagnosis and repair archive.

## 2. 方法论

### 2.1 系统结构与六个可编辑模块
- 系统定义为：  
  **S = (F, B, H)**  
  - F：全双工交互模型，负责实时听说。
  - B：委派池，包含推理 LLM 和编码智能体，异步执行长程任务。
  - H：协作框架，决定任务如何进入实时对话。
- 框架 H 由六个模块组成：  
  **H = (Policy, Intake, Hold, Worker, Deliver, Memory)**

| 模块 | 协作决策 | 可编辑内容 |
|---|---|---|
| Policy | 直接回答、委派或任务控制 | 指令、委派 schema、路由示例 |
| Intake | 识别用户操作及对应的活跃任务 | 解析规则、控制线索、任务关系、消解规则 |
| Hold | 任务进行中用户听到什么 | 回执、进度时机、控制回复 |
| Worker | 选择委派对象、上下文和结果契约 | 路由、任务指令、结果 schema、可执行覆盖 |
| Deliver | 何时以及如何返回当前结果 | 说话窗口、等待策略、成功/失败渲染 |
| Memory | 对话与后台工作共享的上下文 | 轮次组装、保留、压缩、重置恢复 |

- 模块之间通过共享状态协同：
  - **会话引擎**维护任务账本（身份、版本、状态、交付历史），任务可被接受、运行、完成、交付、取消或替换；迟到的旧结果不能重新变为当前任务。
  - **Memory** 保存解释最新请求和给委派足够信息所需的对话上下文。
  - **交互模型适配器** 将框架决策映射到具体模型，但不改变决策含义。

### 2.2 测试对话生成与失败诊断
- 模拟器将框架契约转化为可执行的定时对话：
  - **19 种请求类型**：分为会话、信息、推理、行动四类。
  - **22 种交互模式**：包括正常完成、任务控制（细化、替换、取消、状态查询）、并发工作、全双工重叠（打断、用户说话时结果到达、反向通道）、连续性与恢复（延迟、失败、追问、重置）。
  - 先固定语义期望，再添加语言变化（犹豫、复述、干扰项、数字读法等）和声学变化（噪声、信道效应、说话人风格等）。
- 每次失败运行被赋予一个**失败签名**：  
  **φ(τ) = (cause, module, pattern)**  
  - 诊断器先识别失败标志，再按固定优先级选择最终原因；默认映射给出责任模块，中间决策和返回载荷可以修正归属。
  - 感知失败（交互模型未正确识别输入）不计入框架责任。
- **协作得分 Q**：  
  **Q = 成功对话数 / 有效对话数（排除感知失败）× 100%**  
  在固定核心集和保护集上计算，衡量协调是否正确。

### 2.3 递归改进闭环 Duplex-Harness-RSI
- 每个改进轮次包含：
  1. **Exam Planner**（推理 LLM，如 DeepSeek-v4-flash）根据上一轮归因失败和修复档案调整下一轮测试分布，保持固定核心、代表性覆盖和新增变体预算。
  2. 模拟器生成并运行考试，诊断失败并生成轨迹。
  3. **Harness Editor**（编码智能体，如 Codex）在隔离工作区中，根据可见证据提出针对特定模块的候选修订，生成修改文件和 rationale。
  4. **开发门**：候选在相同考试上与原框架进行配对比较，要求胜出多于失败、保持协作不变量、原因回归在容差内。
  5. **保护门**：通过开发门的候选在隐藏保护集上再次比较，要求至少胜出不少于失败且保持不变量。
  6. 接受的修订成为新的保留版本，失败的尝试也写入修复档案，供后续轮次参考。
- 评估器检查六项不变量，例如：结果只能从交互模型发出、只能交付当前结果一次、不得屏蔽交互模型语音、参考答案不得进入提示等。

## 6. 主要结论与发现

- **DuplexAgent 结合连续交互与复杂任务执行**：
  - 在口语知识方面，VoiceChat 上 OBQA 从 54.2% 提升到 80.6%，MMSU 从 36.1% 提升到 80.5%；Qwen-Realtime 上 OBQA 从 86.3% 提升到 92.1%，MMSU 从 64.8% 提升到 82.7%。
  - 在可执行工具使用方面，VoiceChat 上 BFCL 平均从 53.5% 提升到 75.8%，FDB-v3 Pass@1 从 16.0% 提升到 47.0%；Qwen-Realtime 上 BFCL 平均从 82.0% 提升到 90.8%，FDB-v3 Pass@1 从 39.0% 提升到 49.0%。
  - 全双工时序基本保持或接近附着交互模型水平，部分条件有轻微波动，如 Qwen-Realtime 合成暂停 TOR 从 0.074 上升到 0.147。
- **描述性委派是许多已有系统的失败模式**：
  - Gander、Realtime-Venus-Omni、Qwen-Audio-Agent 等把用户请求改写为自然语言描述或任务标题，导致可执行工具调用丢失，同时可能改善口语知识但工具分下降。
  - DuplexAgent 将“委派决策”与“委派内容”分离，使工具调用保持可执行性。
- **Duplex-Harness-RSI 显著优于其他修订方式**：
  - VoiceChat 固定核心上：初始 g0 为 54.6%，One-shot Editing 为 57.4%，Sequential Editing 为 61.9%，RSI 十轮达到 85.3%。
  - Qwen-Realtime 固定核心上：g0 为 47.1%，八个保留版本后 g8 达到 84.8%，提升 37.7 个百分点。
  - 失败归因显示主要收益来自“恢复委派”错误减少，额外委派略有上升。
- **模块修复具有针对性**：
  - Policy 明确直接回答类别，减少额外委派 50%。
  - Intake 根据实时任务状态处理取消和替换，忽略取消减少 81%，替换失败减少 65% 后进一步减少 83.3%。
  - Hold 提前进度报告，缺失进度更新减少 75%。
  - Worker 保留单位、精度和已验证内容，错误答案减少 66.7%。
  - Deliver 仅在用户沉默时说话并区分失败与成功，重叠和隐藏失败均减少 100%。
  - Memory 组装完整轮次并保留上下文，缺失上下文失败减少 60%。
- 这些修复叠加后显著提升整体协作质量，且未改变交互模型权重。

- **模拟器偏差风险**：内部得分 Q 和失败诊断依赖自动诊断器的规则，如果诊断规则本身存在偏差，可能影响改进方向。
- **对比不完全均衡**：某些对比中不同系统使用不同的委派模型或底层交互模型，虽然论文尽量控制变量，但跨系统比较仍可能受底层模型能力差异影响。
- **统计显著性未报告**：多数性能提升未提供置信区间或显著性检验，少量百分点变化可能受随机性影响。
- **消融范围有限**：One-shot 和 Sequential 的对比主要在 VoiceChat

上报告，Qwen-Realtime 仅展示版本曲线，未与 One-shot/Sequential 直接对比；这限制了不同修订策略在不同交互模型上通用性结论的强度。

- **外部模型依赖与版本漂移**：委派池和 RSI 中的推理、编码能力依赖 DeepSeek-v4-flash、Codex、gpt-5.6-sol 等外部模型，论文未说明这些模型版本如何固定，或在不同时间访问时行为是否一致；若外部模型更新，可能影响框架修订和复现结果。
- **人类主观体验评估缺失**：评价主要基于自动指标和模拟器得分，未包含用户对打断自然度、等待体验、响应及时性、语音重叠处理的主观评分，因此无法完全证明交互体验提升。
- **模块间错误迁移未量化**：虽然提供了模块级修复证据，但没有系统分析一个模块的修改是否会在其他模块或交互模式中引入回归；保护门只针对六项不变量，可能掩盖隐性交互退化。
- **长程记忆与多会话一致性未深入**：Memory 模块涉及保留、压缩、重置恢复，但实验未系统评估跨会话记忆、长期用户偏好和任务连续性，真实长程对话中的漂移和遗忘风险仍不明确。
- **部署开销与实时性未讨论**：框架、模拟器、诊断器、编辑闭环带来的工程复杂性和推理开销未量化；全双工语音系统对延迟敏感，论文未报告端到端延迟或计算成本，实际部署可能难以满足低延迟要求。
- **模块 schema 依赖人工设计**：六模块虽可编辑，但其边界、输入输出契约和默认失败映射仍由人工定义；若未来任务或交互模式超出既有 schema，框架可能需要重新设计，而非自动扩展。
