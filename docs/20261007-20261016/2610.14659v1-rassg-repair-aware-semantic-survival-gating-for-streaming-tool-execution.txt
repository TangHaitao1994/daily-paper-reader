# RASSG: REPAIR-AWARE SEMANTIC SURVIVAL GATING FOR STREAMING TOOL EXECUTION

ABSTRACT 

Streaming speech assistants can launch tools before users finish speaking, overlapping execution with incoming speech to reduce user waiting time. However, subsequent self-corrections can invalidate apparently stable arguments, causing stale execution whose irreversible effects persist even after the final call is corrected. We propose Repair-Aware Semantic Survival Gating (RASSG) to jointly control tool launch and cancellation during streaming speech. RASSG launches a tool when three consecutive speech recognition results arrive with identical nonempty arguments, then combines calibrated argument invalidity risk with execu-tion costs to decide cancellation at the last feasible opportunity before effects become irreversible. Evaluation on ReCAST, FDB-v3, and Audio2Tool uses a controlled execution clock with fixed tool runtimes and cancellation parameters. On ReCAST’s prospective-repair subset, RASSG reduces the stale execution rate from LocalAgreement-2’s 50.00% to 3.15%, with a mean delay of 3.676 s across successful trajectories. The stale reduction also holds against every early-execution baseline on both public speech datasets. Ablations with identical initial launches support active cancellation, showing the value of controlling ongoing calls before their effects become irreversible. Code and data are available at 

https://github.com/daijinhu/RASSG .

Index Terms — Speech agents, tool execution, semantic survival 

1. INTRODUCTION 

Voice assistants are expanding from conversational responses to com-pleting user tasks through external tools [1, 2, 3, 4]. Streaming speech processing lets systems interpret incoming speech incremen-tally and form the intents and arguments needed for tool use [5, 6]. Building on this capability, streaming tool execution allows opera-tions to be prepared and launched before an utterance ends, so that speech understanding and task processing proceed in parallel [7]. This overlap can shorten the time users wait for results and support more responsive, continuous interaction. However, users may correct an argument before finishing their utterance [8], leaving an already launched action inconsistent with their final intent. When an action using a superseded argument crosses its irreversible deadline, it causes stale execution , even if the system eventually completes the correct call. Existing strategies face different limitations in handling this problem. Waiting for the complete utterance postpones work that could begin earlier. Recognition stability, as captured by LocalAgreement [9, 10], supports early output but cannot guarantee that the user will not subsequently revise an argument. Waiting until a replacement argument is fully available before updating an action can miss the cancellation window. Streaming tool execution therefore requires joint consideration of whether the current argument is stable enough to launch and whether execution should continue while the tool remains cancellable. To address the risk of stale execution when users revise argu-ments after tool launch, we propose Repair-Aware Semantic Sur-vival Gating (RASSG). It coordinates early launch and repair han-dling in streaming speech tool use. RASSG launches tools based

Our main contributions are as follows: 1. We characterize execution correctness beyond final call suc-cess by jointly modeling argument versions and irreversible deadlines. This formulation captures stale execution that can coexist with eventual success and makes opportunities for re-pair during execution explicit. 2. We introduce RASSG, which uses observed argument stabil-ity for launch and predicted argument invalidity together with cancellation deadlines for cancellation. This design lets the system act on stable input while continuing to assess whether an action should be withdrawn in response to subsequent re-pairs. 3. We demonstrate reductions in stale execution and successful delay in controlled synthetic speech experiments relative to a control with identical initial launches and no active cancel-lation. Component and execution-semantics analyses identify the roles of launch stability, cancellation signals, and progress reuse, providing empirical evidence for the risk–latency trade-off in streaming tool execution. 

2. RELATED WORK 

Tool execution after complete input generates calls from a full utter-ance or a received dialogue turn. Speech-to-tool systems either map audio directly to calls or transcribe speech before parsing tools and arXiv:2610.14659v1 [cs.AI] 10 Oct 2026 arguments [1]. When requests lack necessary information, clarifi-cation methods recover unspecified intents and correct errors across turns [11]. Related benchmarks examine goal revisions, missing pa-rameters, argument correction, and recovery from tool failures [12, 13]. These developments improve the handling of incomplete or re-vised requests using available dialogue context. However, workflows that wait for the complete utterance leave tool processing until after the user finishes speaking. Early execution from incremental input overlaps processing with ongoing speech. Incremental dialogue and streaming transcription provide mechanisms for revision propagation and stable-prefix con-firmation [14, 10]. Related approaches move response generation and reasoning into the input period through speculative computation or semantic triggering [15, 16], while speech agents interleave or synchronize reasoning and tool actions with incoming audio [6, 2]. Two works directly address changes to early calls. Stream RAG [7] generates queries during speech; its model-triggered variant termi-nates earlier queries when a new one is issued. Speculative Interac-tion Agents [17] handles user input and tool returns asynchronously, permits modification or removal of unfinished calls, and defers sen-sitive tool execution until confirmation. These mechanisms establish support for revising or withdrawing speculative calls. For tools that permit cancellation within a finite window, the remaining decision concerns whether an ongoing action should continue given future ar-gument invalidity, cancellation cost, and the time remaining before irreversibility. Evaluation has also expanded beyond isolated call accuracy to cover conversational correction and execution progress. Stateful and speech-based tool benchmarks collectively assess intermediate states, repairs in human speech, and verifiable task completion during full-duplex interaction [18, 8, 19, 20]. These evaluations provide a basis for examining how evolving intent affects ongoing tool use. Within the incremental execution approach, RASSG focuses on cancellation decisions under finite tool deadlines. It uses observed argument stability for launch and predicted argument invalidity for cancellation, accounting for actual recognition arrivals and cancellation acknowledgements. This connects the decision to continue or withdraw an action with the joint evaluation of stale execution and successful delay. 

3. METHODOLOGY 

RASSG coordinates early tool launch with repairs during execution. As shown in Fig. 2, parsed arguments feed stability-based launch and invalidity prediction, while newly recognized arguments update active calls. The controller combines calibrated risk with tool con-figuration and execution state to decide whether to cancel at the last feasible opportunity before the current version becomes irreversible.

4. EXPERIMENTS 4.1. Dataset Design 

We construct ReCAST (Repair and Early Commitment Assessment for Streaming Tools), a synthetic speech dataset for evaluating early execution and subsequent repairs. Time, amount, location, and contact requests cover ordinary speech and different repair timings. Stable and corrected pairs share audio before branching. Source data contain 320 training and 128 development recordings. Speech-connected groups divide development equally into model-selection and policy-calibration sets. The test set contains 2,400 recordings from two new voices and new templates, with 1,200 prospective-repair recordings used for the main comparison. Public evaluation covers all 100 FDB-v3 recordings [8], and 2,145 Audio2Tool Tier 6 correction queries meeting the input-duration limit [1], with one released rendition per query. 

4.2. Baselines 

We compare RASSG with five baselines: End-of-Utterance Exe-cution, LocalAgreement-2, Confidence commit, and adaptations of Stream RAG and Speculative Tool Calling. End-of-Utterance Execution (EOU) waits for speech to end and final recognition to arrive. LocalAgreement-2 [9, 10] launches after argument agreement across two actual ASR arrivals. Confidence commit [24] is our threshold control using source-selected confidence 0.95 .Stream RAG [7] launches parallel calls for each arriving nonempty block proposal, including duplicates, then selects the earliest call matching the final observed plan and cancels unfinished alternatives at EOU. Speculative Tool Calling [17] executes the first proposal immediately. Changed arguments trigger withdrawal and fresh execution after acknowledgement. Stream RAG assumes parallel tool capacity. Speculative Tool Calling evaluates eager execution, while its final-confirmation branch reduces to EOU under our atomic-plan representation. 

4.3. Evaluation Setup 

All policies share Whisper small.en [25] prefixes decoded every 960 ms. ReCAST uses a fixed-lexicon parser. Public speech uses Qwen2.5-3B-Instruct [26] with 4-bit weights to parse current prefixes and public tool schemas into complete plans. Arrivals include measured frontend service times. We execute tool calls within an event-clock execution model that processes commitment, update, cancellation acknowledgement, and irreversible-boundary events. Tool runtimes and cancellation costs are static configuration parameters. Control intervals, processing budgets, and acknowl-edgement delays are 320, 10, and 20 ms. Timely U PDATE reuses progress. Restarting after C ANCEL does not. We report two metrics. Stale execution rate is the fraction of all trajectories with at least one stale execution. Successful delay is measured only when the final argument is correct and an active call exists. Its origin is final-argument acoustic availability for ReCAST and waveform end for public speech, with negative values clipped to zero. Because these origins differ, delay comparisons are made within each dataset. Table delay means condition on each policy’s own successful trajectories, whereas stale execution retains all tra-jectories.

5.2. Ablation Study 

Table 2 separates component removals from launch consensus. With first commitments and reactive argument updates fixed, removing ac-tive cancellation raises stale execution from 3.15% to 49.92%. Can-cellation reduces stale execution by 46.77 percentage points, with a 95% interval of [45.71, 47.78], and common-success delay by 0.758 s [0.702, 0.815]. The gain therefore comes from controlling an ongoing call, rather than delaying its first launch. Removing progress reuse increases successful delay from 3.676 to 4.510 s, a paired penalty of 0.834 s [0.788, 0.881]. Its stale rate falls slightly, from 3.15% to 3.06%, because restarting can move the irreversible boundary later. The 0.083-percentage-point reduc-tion comes from one recording across eight actions and three check-points, with a paired 95% interval of [0.000, 0.256]. Progress reuse primarily saves waiting. Consensus controls how much speech evidence precedes launch. Moving from two to three arrivals removes 13.71 percentage points of stale execution for 0.402 s additional waiting; moving from three to four removes another 2.27 points for 0.774 s. The fourth arrival costs more delay for a smaller absolute risk reduction. We adopt three-arrival consensus as the risk–delay operating point studied here and report the trade-offs of all other evaluated consensus settings. 

5.3. Results Analysis 

The method separates launch evidence from continuation risk. Argu-ment agreement filters transient proposals before commitment; cal-ibrated invalidity forecasts supersession after launch. Launch-only confidence or agreement rules do not make this second decision, and replacement-triggered withdrawal waits for the new argument. RASSG can act before replacement resolution, using the deadline and reusable progress to determine whether intervention remains fea-sible and its predicted benefit exceeds discarded work. ReCAST’s matched-launch trajectories directly support this mechanism. Among 28,800 recording–action–checkpoint combina-tions, cancellation removes stale execution from 13,470 trajectories without introducing a newly stale trajectory. In every avoided case, cancellation precedes the no-cancellation control’s first irreversible error. Late replacements fall from 14,304 to 834: withdrawal fol-lowed by recommitment renews the version’s cancellation window, allowing more subsequent corrections to arrive in time. Timely up-dates preserve valid work, explaining why stale reduction coincides with shorter delay. The reuse removal verifies this division of roles: the veto protects argument versions, while retained computation supplies the latency benefit. 

6. CONCLUSION 

RASSG combines argument-consensus launch with calibrated, deadline-aware cancellation. Under fixed execution parameters, it reduces stale execution relative to early-execution baselines across three speech datasets. Matched-launch removal experiments distin-guish the protection supplied by cancellation from the waiting-time reduction supplied by progress reuse. Beyond three arrivals, further confirmation costs more waiting for less absolute risk reduction. Execution control must therefore remain responsive to repairs after launch. 

7. COMPLIANCE WITH ETHICAL STANDARDS 

The reported experiments use synthetic ReCAST speech and the pub-licly released FDB-v3 and Audio2Tool datasets [8, 1]. They involve no participant recruitment, collection of new human recordings, or intervention with human participants.
