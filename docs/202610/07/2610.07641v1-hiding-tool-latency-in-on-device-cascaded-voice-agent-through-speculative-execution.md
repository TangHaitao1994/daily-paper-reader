## 摘要
工具增强的语音助手通常串行执行自动语音识别、大语言模型推理和外部工具执行。因此，工具延迟仅在用户说完并且大语言模型识别出所需工具调用之后才会产生。我们提出了面向端侧级联语音代理的投机工具执行方法，该方法从部分 ASR 假设中预测工具请求，并在语音仍在接收时启动工具执行，从而降低端到端响应延迟。我们的方法引入了一个预测器模块，在语音识别过程中预判工具调用，投机地执行它们并缓存结果。随后将缓存输出注入大语言模型提示中，以实现更快的响应。此外，为减轻用户说话时自我纠正带来的错误，我们采用基于规则的验证机制，仅选择性地注入有效的缓存结果。作为最终保障，大语言模型保留直接发起工具调用的能力，确保在最坏情况下我们框架的延迟上限不超过基线串行执行流水线。我们使用完全实现的 Android 语音助手的实测数据来评估我们的方法。我们的方法将首次音频响应的中位时间从 5.79 秒降至 4.60 秒，并将标准差从 3.49 秒降至 2.81 秒，从而获得更可预测的响应延迟。

## Abstract
Tool-augmented speech assistants typically serialize automatic speech recognition, large language model inference, and external tool execution. As a result, tool latency is incurred only after the user has finished speaking and the LLM has identified the required tool calls. We present speculative tool execution for on-device cascaded voice agents, which predicts tool requests from partial ASR hypotheses and initiates tool execution while speech is still being received, thereby reducing end-to-end response latency. Our approach introduces a Predictor module that anticipates tool calls during speech recognition, executes them speculatively, and caches the results. The cached outputs are then injected into the LLM prompt, enabling faster responses. Additionally, to mitigate errors caused by user self-corrections during speech, we employ a rule-based validation mechanism that selectively injects only valid cached results. As a final safeguard, the LLM retains the ability to issue tool calls directly, ensuring that the latency of our framework is upper-bounded by the baseline serial execution pipeline in the worst case. We evaluate our method using live measurements from a fully implemented Android voice assistant. Our approach reduces the median time-to-first-audio from 5.79,s to 4.60,s and decreases the standard deviation from 3.49,s to 2.81,s, resulting in more predictable response latency.

## 1. 论文的核心问题与整体含义

- **研究背景**：工具增强型语音助手通常采用级联结构：ASR（自动语音识别）→ LLM（大语言模型）→ 工具执行 → LLM 生成回复 → TTS（语音合成）。工具调用必须等用户说完、ASR 完成、LLM 判断出工具需求之后才能开始，导致远程工具（如网络搜索）延迟直接叠加在用户可感知的响应时间上。
- **核心问题**：如何在不牺牲可靠性的前提下，减少级联语音代理中由外部工具调用引起的端到端响应延迟。
- **整体含义**：论文提出一种**投机执行（speculative execution）**方法，在用户还在说话时，利用流式 ASR 的部分识别结果提前预测可能要调用的工具，并提前执行、缓存结果。这样就能把工具延迟隐藏在剩余语音输入时间内，从而降低用户说完话到听到回复之间的等待时间，同时保证最坏情况下不差于串行基线。

## 2. 论文提出的方法论

- **核心思想**：把流式语音视为提前计算的信号来源，在 ASR 阶段就启动只读工具调用，将工具执行与语音输入过程重叠。

- **关键模块：Predictor（预测器）**
  - 观察流式 ASR 的部分假设（partial hypotheses）。
  - 触发条件：至少观察到 `N_min = 6` 个词后；之后每增加 `ΔN = 5` 个词触发一次；或检测到超过 `τ_pause = 300ms` 的句间停顿。
  - 将当前部分假设按子句分割，分割依据包括句末标点以及 `and`、`but`、`also`、`then`、`while` 等并列表达。
  - 每个子句独立分析，输出候选元组 `(tool, topic, query)`，例如 `(searchWeb, weather, "weather in Boston")`。
  - `topic` 来自固定 12 个粗粒度信息寻求类别，支持单句中的多个搜索意图并行派出投机调用。

- **缓存与注入机制**
  - 在 `t_ASR`（ASR 完成）时，将最终转录文本与已完成的投机工具结果直接插入 LLM 提示词。
  - LLM 可以基于缓存结果直接生成回复；如果 LLM 仍然发出工具调用，则先检查缓存中是否已有匹配结果。
  - 命中则直接复用缓存，避免重复请求；未命中则走正常工具执行路径。

- **安全保障**
  - LLM 保留直接发起工具调用的能力，作为兜底。
  - 因此框架的延迟在最坏情况下不超过串行基线。
  - 投机调用限制在只读工具上，避免错误修改日历、闹钟等用户数据。

- **流水线形式**：
  - 串行基线：`t0 < t_ASR < t_LLM-call < t_Tool < t_LLM-resp < t_TTS`
  - 投机方法的目标：把 `t_Tool - t_ASR` 的一部分或全部隐藏在 ASR 剩余时间内，从而降低 `t_TTS - t0`。

## 6. 论文的主要结论与发现

- **延迟显著降低**：中位 TTFA 从 5.79s 降至 4.60s；平均 TTFA 从 6.69s 降至 5.99s；标准差从 3.49s 降至 2.81s。
- **尾延迟改善明显**：TTFA p99 从 19.76s 降至 15.10s；首次工具调用时间 FT p99 从 22.44s 降至 11.71s。
- **工具选择准确率提高**：F1 从 44.8% 提升到 60.6%。
- **直接缓存注入是准确率提升主因**：为较小的 3B 量化 LLM 提供额外上下文，发挥了类似 in-context learning 的作用，改善了工具选择。
- **验证回退提高缓存复用**：减少了冗余工具调用和浪费的投机调用。
- **鲁棒性可接受**：硬负样本假读率仅 9.1%；对抗样本 F1 达 90.2%，假读率 12.3%。由于投机仅限只读工具，错误不会修改用户数据。
- **规则预测器更务实**：离线来看 LLM 预测器精度更高，但其推理开销会挤占 NPU 资源，难以在用户说话结束前稳定完成预测，因此轻量规则预测器更适合端侧部署。

## 7. 优点

- **创新地利用流式 ASR 进行预测性计算**：把用户说话时间变成隐藏远程工具延迟的机会窗口，思路直观有效。
- **系统设计完整且有安全网**：包含直接注入、缓存验证回退、LLM 保留标准工具调用路径，最坏情况延迟有上界，实际可用性强。
- **真实端侧实测**：在商用手机上完整实现并测量，不是纯模拟，结果具有工程参考价值。
- **关注用户自我纠正等现实问题**：通过硬负样本和对抗样本评估误触发、撤销等场景，鲁棒性考虑较全面。
- **消融实验清晰**：逐步拆分各组件贡献，明确了直接注入和验证回退各自的作用。

## 8. 不足与局限

- **数据集偏小且单一**：共 146 条英语样本，覆盖场景有限，难以代表真实世界语音助手的多样性。
- **缺少与已有方法的直接对比**：仅与自身串行基线比较，未与流式工具调用、并行工具执行等相关工作做 benchmark 对比。
- **单设备评估**：只在 Galaxy S26 Ultra 一款高端设备上测试，结果可能过度依赖硬件性能，无法推广到中低端设备。
- **指标聚焦延迟和工具选择**：没有充分评估最终回答的事实正确性、用户满意度、多轮交互质量等。
- **规则预测器扩展性有限**：依赖固定 12 个 topic 和基于标点/连接词的子句分割，对复杂意图、多轮状态和不同语言的支持可能不足。
- **未报告资源消耗**：缺少能耗、内存占用、NPU/CPU 竞争对系统的影响分析。
- **语音输入为合成 TTS**：与真实用户口音、语速、停顿等自然语音特征可能存在差距。
- **安全边界依赖工具只读限制**：若扩展到写操作工具，投机错误的后果将更严重，当前设计无法直接覆盖。
