Interactive models increasingly hand complex reasoning and tool use to a slow brain in the back-ground, leaving a realtime front model free to sustain full-duplex dialogue. Yet the user may refine, cancel or replace a request while its task runs, so a plan or result that made sense a moment ago goes stale. Each new utterance must therefore be read against the work in flight, but the front model follows only the conversation and the back end sees only its own task. Coordination deserves a brain of its own, one that sees both. We introduce Jarvis, a coordination harness where models judge and code enforces. Its typed decision model, JEV, reads each turn against the live tasks and picks among operations built from a versioned task record. Code checks every choice against the current state before applying it, so no decision can act on a task version the user has replaced. Jarvis also rechecks plans before they execute and results before they are spoken, and counts an answer as delivered only once the user has heard it in full. We build two instances of this design. Jarvis-Audio runs unchanged on three full-duplex speech models. Jarvis-Omni adds vision and rechecks the evidence behind an answer before and during playback, since a scene can change while nobody speaks. With the front model and back end held fixed, replacing Qwen Audio Agent with Jarvis raises 𝜏 -Voice task success more than sixfold, from 29 to 192 of 278 tasks, and the gains hold on every benchmark and front model. Against published systems, Jarvis-Audio reaches 69% Pass@1 on Full-Duplex-Bench v3 with an open 9B front model, versus 60% for GPT-Realtime. These results suggest that how the two brains are coordinated matters as much as how strong they are.

## 1. Introduction 

Full-duplex speech models have changed what it feels like to talk to a machine. Systems such as Moshi (Défossez et al., 2024), MiniCPM-o 4.5 (Cui et al., 2026), Realtime-Venus (Ant Group, 2026), GPT-Realtime (OpenAI, 2025) and Gemini Live (Google DeepMind, 2026) listen while they speak, take the floor at natural moments and stop when the user cuts in. As conversation becomes this natural, users expect these assistants to do real work as well, such as building a small party game, fixing a bug or remembering their usual snack budget. In games, they want a teammate that watches the match, suggests the next move and plays for them when asked. Such requests need tools, multi-step reasoning and long-term memory, more than a realtime model of a few billion parameters can supply while it keeps pace with the conversation. Agentic interactive models close this gap with a division of labor. A realtime front model, the fast brain , keeps the conversation going, while a slow brain , either a larger model or a full agent harness, reasons and uses tools in the background (Ant Group, 2026; OpenAI, 2026; Orantqing et al., 2026; QwenAudio Team, 2026; Wu et al., 2025). This split mirrors the fast and slow modes of human thinking (Kahneman, 2011) and solves the capacity problem but creates a new one. Background work takes seconds or minutes, and the conversation does not wait. While a task runs, the user may refine, cancel or replace it, so a plan or result that made sense a moment ago goes stale. Figure 2 shows what this means in practice. In a session recorded with Jarvis, the harness we propose 1,the user asks in one breath for a browser game, tonight’s weather in Shanghai and two technology headlines. Over four minutes the game is reshaped three times to add two players on one phone, a shared score with quick respawns and a light theme that also becomes the saved default. In between come a Python question with a follow-up, a sixty-dollar snack budget for tonight that leaves the usual forty intact, and a welcome sign that is later cancelled while everything else keeps running. None of these utterances stands on its own. Each must be read against up to four tasks already in flight, so every time the system has to answer three questions. Does the utterance start new work or change a running task, and which one? Is a finished result still what the user wants? And did the user hear the whole answer, or was it cut off? These are coordination decisions, yet current systems leave them to a component whose main job lies elsewhere. End-to-end models make them while they speak (Google DeepMind, 2026; OpenAI, 2025), with only the text in their context to tell which task version is still live. Harnesses with a fast and a slow brain hand them to one of the two. The front model can emit task calls while it replies (Ant Group, 2026; Orantqing et al., 2026) but cannot see task versions. The backend agent can decide while reasoning about its task (QwenAudio Team, 2026) but does not follow the conversation. One hears every word and the other knows the task, but coordination needs both. A task manager alone does not close this gap. Qwen Audio Agent (QAA) (QwenAudio Team, 2026) already tracks tasks, supports cancellation and collects playback receipts, yet a model still writes the call that maps an utterance to a task, and nothing checks that its target exists or is still current when it takes effect. “Make it sixty dollars” can then change the game instead of the snack plan, a correction can land on a replaced version, and a late draft can be played after the user has moved on. Table 1 lists six such failure modes, five with audio alone and a sixth once the agent can see. These failures occur even when recognition is accurate and every worker reasons correctly about its request. The problem is timing. Because the two brains run at different speeds, a decision can rest on an incomplete view of the work or outlive the state that justified it. Better recognition and reasoning

We therefore argue that coordination deserves a brain of its own, one that sees both the conversation and the live tasks, backed by a runtime that enforces its decisions. Our guiding rule is models judge, code enforces .We propose Jarvis, a coordination harness built on this rule. Every request becomes a task in the Task Ledger, a versioned record of what the user asked for and what happened to it, and every change becomes an operation on that ledger, such as refining version 3 of the game. A typed decision model, JEV 2, reads the new turn against the live tasks and picks among operations the runtime builds from the ledger, never writing one itself. Code checks the task and version of each pick before applying it, so no choice can name a missing task, and one aimed at a replaced version becomes a no-op. The same rule runs through the rest of the harness. The Native Gate, trained on the front model’s control tokens, decides when a turn goes to the slow brain without touching speech weights. If JEV is unsure, no task changes and a worker answers or asks the user to clarify. The Task Ledger accepts results only for live versions and rechecks plans against the conversation before they run, so stale work cannot take effect just because a worker finished. Delivery marks an answer delivered only after playback receipts show it played in full, and stopping the voice does not cancel the work behind it. Memory saves “usually forty” as a lasting fact and leaves “only sixty tonight” on the snack task. We build two instances of this design. Jarvis-Audio is built mainly on Realtime-Venus-Audio, and the same harness runs unchanged on MiniCPM-o 4.5 and NVIDIA’s VoiceChat-11B (NVIDIA, 2026).

2.1. What Goes Wrong Without Coordination 

Running background work under a live conversation produces its own class of errors. They are not recognition errors and not reasoning errors. They happen because two processes move at different speeds and nothing keeps them in step. Table 1 lists the six failure modes we see. The first five arise with audio alone, and the sixth appears once the agent can see. All six share one cause. The system acts on a picture of the conversation that has stopped being true, whether that picture is a task version, a plan, a playback state, a remembered fact or a frame of video. Patching each case with prompt rules does not scale, because every new situation produces a new variant. Jarvis removes the cause instead. It makes the current state explicit and checks every action against it. 

2.2. Design Principles 

Four principles follow, and every module of Jarvis applies at least one of them. 1. Learn when , keep how . The front model already speaks well. We train only the decision of when to involve the slow brain, on the model’s own control tokens, and leave every weight that produces speech frozen. 2. Models judge, code enforces. Questions that need understanding go to a decision model, but the model answers by choosing among operations that the runtime has prepared. The runtime then applies the chosen operation and checks it against the current state. 3. Nothing is assumed current. Plans, results, playback and visual facts all carry a version, an epoch or a timestamp, and each is checked again before it may act or speak. 4. Done is not delivered. A worker finishing a task and the user hearing the answer are two separate events, and the system records them separately.

2.3. How a Request Flows 

Figure 3 shows the path of a request. Audio reaches the front model and a streaming ASR observer at the same time. For every one-second audio unit, the Native Gate reads the control state of the front model and chooses to keep listening, to let the front model answer on its own, or to hand the turn to the slow brain. Small talk and short answers therefore stay fast. A hand-off carries the audio sample at which it was made, so the slow brain works from the transcript of what the user actually said rather than from text the front model generated. JEV selects operations, the Task Ledger applies them and runs workers, and Delivery speaks accepted results in the front model’s own voice. The two brains never wait for each other. The fast brain keeps talking while three workers run, and the slow brain updates its tasks while the user is still speaking. This design has two instances. Jarvis-Audio, the main subject of this report, runs on full-duplex speech models. Jarvis-Omni runs on Venus-Omni, which also watches the screen. It keeps the Task Ledger, the workers and Delivery unchanged, replaces JEV with the multimodal Jev-Omni, and adds the dashed perception layer of Figure 3, which keeps visual facts together with the time they stop being valid. Section 3 describes the modules in Jarvis-Audio, Section 4 shows what changes when the front model can see, and Table 9 in Appendix A compares the two instances side by side. 

## 3. The Jarvis Harness 

This section follows the game night of Figure 2 through the five modules of Jarvis, as they run in Jarvis-Audio on Realtime-Venus-Audio (Ant Group, 2026). Venus-Audio is a 9B full-duplex model that follows the Omni-Flow design of MiniCPM-o 4.5. A Whisper-Medium encoder feeds a Qwen3-8B Thinker, whose text and hidden states drive a streaming Talker. The model consumes audio in one-second units, predicts at every unit whether to listen or to speak, and has a native <delegate> 

token for handing work to a backend. We use the released checkpoint as the fast brain, and apart from a small control adapter none of its weights change. 

3.1. Native Gate: Learning When to Hand Off 

The first decision in every turn is whether the slow brain should be involved at all. “Build me a little game for tonight” needs it, “tell me a joke” does not, and “hold on, let me ask my roommate” is not addressed to the assistant. The decision has to be made from audio while the user may still be talking, and a rule on top of ASR cannot make it well, because the words alone do not tell a finished request from a pause. The front model already carries the information that matters, since it is the part of the system that decides when to speak. The Native Gate therefore reads its decision directly from the front model’s native control tokens.

Binding the turn. The gate decides when, and a streaming ASR observer, Qwen3-ASR-1.7B (Shi et al., 2026), supplies the words. When the gate fires DELEGATE , the event records the audio sample at which the decision was made, and the runtime attaches the most recent final transcript that started before that sample. The slow brain thus receives what the user actually said, including names, numbers and spelled identifiers, rather than a paraphrase generated by the front model.

The typed interface. A request to JEV consists of a state and a set of typed questions. The state holds the bound transcript, the last twelve turns, any question the assistant is waiting on, the user profile and the available tools. Each question belongs to one of three primitives. A Choice question lists named options and returns a probability distribution over them. A Noul question returns the probability of yes for a single statement. A Score question returns an expected value on an ordinal scale. None of them returns free text, so every answer is an option the runtime wrote or a number.

3.3. Task Ledger and Workers 

The Task Ledger is the single place where Jarvis records what the user has asked for and what has happened to it. Each task has an identifier, a version and a logical request identifier derived from the utterance that created it. Tasks created by the same utterance share a request group and keep their order, so the three requests in the first turn of Figure 2 remain three tasks that report back in a sensible sequence. A task moves through the eight states of Figure 6. 

Invariants. The ledger enforces four invariants, and together they rule out the first three failure modes of Table 1. 

I1. One live version. When the user asks for a shared score, version 2 of the game becomes version 3 and version 2 moves to SUPERSEDED . At most one version of a request is live at any time, and a repeated utterance creates no duplicate. 

I2. Late results are rejected. A worker result is accepted only if its task version is live. A slow draft of version 2 that finishes after the user asked for version 3 is discarded and logged, and it can never be presented. 

I3. Plans are checked against the conversation. A worker records the conversation snapshot it planned from, and before it executes a planned action the runtime compares that snapshot with the current

one. If the user has corrected an order number or withdrawn an authorization in the meantime, the old plan does not run and the worker plans again. 

I4. Delivery needs a receipt. A task becomes DELIVERED only through a complete playback receipt (Section 3.4). Section 5.4 removes the checks behind I2 to I4 one at a time and measures what each prevents. 

Workers. Each task runs in an asynchronous tool loop built on DeepSeek-V4-Flash (DeepSeek-AI, 2026), with up to three workers at once. Tool results are treated as evidence and never as new instructions, a repeated identical call returns the earlier receipt instead of running again, and a worker asks the user for a missing detail instead of guessing. A worker often produces files, such as the page of the browser game. The runtime builds the list of these files only from writes that the file tool has confirmed, never from what the model says it has written, so the assistant cannot tell the user about a file that does not exist. 

3.4. Delivery: From Done to Heard 

A finished result is not yet an answer the user has received. Suppose the weather report starts playing and the user cuts in after three words to change the game. If the system marks the weather as delivered, the user never hears it and the assistant believes it has answered. Delivery keeps these two events apart with two mechanisms. 

Generation epochs. Every time playback is cleared, for example because the user started speaking or said “stop”, the runtime opens a new generation epoch. Every audio chunk and control message carries the epoch in which it was produced, and messages from an older epoch are dropped on arrival. Audio that was already in flight therefore cannot resume after the user has moved on. 

Playback receipts. The client reports what it has actually played as a stream of receipts, each naming the epoch, the chunk, the number of samples played and whether playback was interrupted. Stopping is not cancelling. “Stop talking” and “cancel that” mean different things, and Jarvis keeps them apart. Stopping the voice opens a new epoch and holds pending announcements, while every task keeps running and keeps its result. 3.5. Memory: Durable Facts Without Drift 

A voice assistant that people use every day should remember what they tell it, but not everything they say. “I usually spend forty dollars” is a fact worth keeping. “Only sixty tonight” is a condition on tonight’s task, and “tell him I’ll call back” was not said to the assistant at all.

Memory keeps two stores per user that persist across sessions. The profile store holds personal facts and preferences, each with a validity period and a link to any record it replaces. The task store holds past tasks with their versions, results and files. Nothing enters the profile unless decision brain agrees, in a Choice question with a threshold of 0.8, that the speaker is explicitly stating a lasting fact about themselves or asking the assistant to remember one. Conditions that belong to a task stay on the task. In Figure 2, “only sixty dollars tonight” refines the snack task while “keep forty as my usual limit” is saved, and a new session opened later still answers that the usual budget is forty dollars. Only an explicit correction can replace a saved record, and the assistant says that something has been saved only after the write has been confirmed. The profile is loaded into every decision, and task records and older facts are retrieved on demand, with decision brain keeping at most three of twelve candidates (Section 5.5). 

## 4. Jarvis-Omni: When Evidence Expires 

Giving the assistant eyes changes the coordination problem in one important way. In audio, the facts behind a decision are mostly in the user’s words, and words do not change after they are spoken. On a screen, facts change on their own. A player asks whether to push forward while a teammate is alive, and two seconds later the teammate is dead. A health bar that was low is full again after a recall. Advice that was right when the question was asked can be wrong by the time it is spoken. Jarvis-Omni is our audio-visual instance of Jarvis, built on Venus-Omni (Ant Group, 2026). It treats visual facts the way Jarvis-Audio treats tasks, as state with a version and a lifetime, and checks them again before anything based on them reaches the user. The harness carries over almost unchanged. Jarvis-Omni uses the same Task Ledger, playback control and typed controller as Jarvis-Audio, so tasks, versions, epochs and receipts behave identically, and the four principles of Section 2.2 apply as they are. Three parts are new, namely a perception layer that records what the system has seen and how long it stays true, a multimodal decision brain that can look at frames, and a gate that also decides when the screen itself deserves a comment. 

4.1. Evidence Timeline and Belief State 

All media enter an Evidence Timeline that keeps screen frames, game audio and the microphone on separate tracks aligned to one clock. Every decision reads a window that ends at the decision time, so no model ever sees a frame from the future. A new match or scene opens a new scene epoch and clears the window, so media from an earlier scene cannot leak into the current one. What the system concludes from these media lives in a Belief State of evidence claims, such as “the teammate on the left is alive” or “my health is low”. Each claim records the observations it rests on, the time until which it is valid and the events that invalidate it, namely a change of scene, a change of camera, a lost source or a correction from the user. A claim may support a current decision only while it is valid and none of these events has occurred. When a response is ready, its claims are checked again. If one has expired, the response is discarded before playback, and if one expires while the response is playing, playback stops at that moment. Figure 7 shows how this unfolds over a few seconds of play. Questions about the past, such as “why did you tell me to retreat?”, are answered from a historical snapshot of the readings behind the advice, framed as what was on screen then, and a claim from a snapshot can never serve as current evidence.

4.2. A Multimodal Decision Brain 

The decision brain of Jarvis-Omni is Jev-Omni, the multimodal member of the JEV family, a 12B typed judgment model built on Gemma 4 (Gemma Team, 2026). It answers the same Choice, Noul and Score questions as JEV, and its inputs may include causal still frames or a short causal audio window. Because the interface is the same, every decision of Jarvis-Audio works in Jarvis-Omni without changes to the runtime. Two new decisions use the images. One reviews whether a frame supports a visual claim and whether that claim is still fresh, and the other chooses the tactical advice that fits the current screen. Game HUDs are dense and small, so Jev-Omni carries light adapters of about 8.5M parameters each for reading the HUD and for telling whether the player’s character is alive. Open-ended descriptions of the screen are proposed by a separate vision-language model, Gemma-4-12B-IT (Gemma Team, 2026) 4, but they must pass this review before they can support anything the assistant says. Not every question needs the full slow brain. “Should I push now?” in the middle of a fight needs an answer within about two seconds. For such questions Jev-Omni reads the latest screenshot and picks the advice that fits it, an independent review confirms that the screen supports the advice, and the front model speaks it. In recorded sessions this fast path starts speaking about 2.2 s after the user finishes the question. Open questions, requests to remember something and questions about earlier rounds go through the full path with workers, tools and in-match memory (Appendix A.2). 

4.3. A Gate That Also Watches 

The gate of Jarvis-Omni follows the recipe of Section 3.1 with a richer causal input. It combines microphone and screen features with the dialogue so far, including the assistant audio that was actually played, and leaves out the transcript of the current utterance. It can also emit a fourth action, 

SCENE , which starts an analysis of the screen without any user request so the assistant can speak up when something important happens. We trained the rank-8 adapter with GRPO on 1,211 episodes built from 49 recorded game sessions. On a fixed test set of 96 episodes, the frozen control head of Venus-Omni makes the right decision in 30 cases and misses an action it should have taken in 66. Our adapter reaches 75 correct with a single missed action, against 67 and 22 for an earlier adapter without dialogue context. ## 5. Experiments 

Our experiments answer three questions. Does the harness by itself make a voice agent better, with everything else held fixed (§5.2)? How does the result compare with the strongest published voice systems (§5.3)? And why does it work, mechanism by mechanism (§5.4 and §5.5)? We close by asking whether the same ideas carry over to vision (§5.6). 

5.1. Setup Benchmarks. 𝜏 -Voice (Ray et al., 2026) runs the customer-service tasks of 𝜏 2-bench (Barres et al., 2025) as full-duplex voice calls with a simulated caller. We use all 278 regular tasks in airline, retail and telecom, and a task counts as solved only when the official reward, which checks the final database state and the required actions, equals 1. Full-Duplex-Bench v3 (Lin et al., 2026) (FDB-v3) plays 100 real recordings of people asking for multi-step tool use with natural disfluencies. 5.5. Memory 

We ask 80 fixed questions about 20 complete ContextDialog conversations, feed the history as real audio and score the answer that was actually played. Both memory back ends of Jarvis score close to 3 points higher than the default memory of QAA (Table 7), with a conversation-clustered interval of [2.43 , 3.05 ] for the gain of JEV selection. QAA compresses the conversation into short notes and passes only 55 tokens of evidence, which loses the details the questions ask about, while Jarvis keeps what both speakers said. The two back ends differ in how much evidence they pass on. JEV selection keeps only the records it judges relevant, while the hybrid retriever passes on more of what it finds. ## 7. Related Work 

Full-duplex spoken dialogue. Spoken dialogue has moved from turn-based pipelines to models that listen and speak at once, from dGSLM (Nguyen et al., 2023) and SyncLLM (Veluri et al., 2024) to Moshi (Défossez et al., 2024), Freeze-Omni (Wang et al., 2024), MiniCPM-o 4.5 (Cui et al., 2026), Seeduplex (ByteDance Seed Team, 2026b), BayLing-Duplex (Fang et al., 2026) and Realtime-Venus (Ant Group, 2026), with omni models extending the idea to video (ByteDance Seed Team, 2026a; Qwen Team, 2026; Xu et al., 2025). Benchmarks have moved from turn-taking (Lin et al., 2025b) to instruction following (Lin et al., 2025a) and tool use (Lin et al., 2026; Ray et al., 2026). These models settle when to speak, and Jarvis builds on them to decide what to do with an utterance once the system acts on it. 

Fast and slow voice agents. Many recent systems pair a realtime model with a stronger background model (Huang et al., 2026; OpenAI, 2026; Thinking Machines Lab, 2026; Wu et al., 2025). Realtime-Venus delegates through a native token (Ant Group, 2026), Qwen Audio Agent (QwenAudio Team, 2026) offers a runtime with a task manager and playback receipts, Gander (Orantqing et al., 2026) lets the front model emit task calls to a Brain, and MoshiRAG (Chien et al., 2026) retrieves knowledge while Moshi keeps talking. Jarvis shares the split but differs in where coordination is decided. A dedicated decision brain selects among operations bound to task versions, and the hand-off is learned on the front model’s native control branch instead of being prompted. 

> 20 Jarvis: Coordination Deserves a Brain of Its Own in Agentic Interactive Models

Dialogue state, typed decisions and memory. Task-oriented dialogue has long tracked explicit slot states (Budzianowski et al., 2018; Wu et al., 2019). Jarvis tracks asynchronous tasks with versions and delivery status instead, updated while the work is still running. Tool-using models (Patil et al., 2024; Schick et al., 2023; Yao et al., 2023) and LLM judges (Zheng et al., 2023) show that models can choose actions and grade outputs, and JEV turns this into distributions over runtime-supplied options that are easy to threshold and audit. Agent memory ranges from retrieval (Lewis et al., 2020) to self-managed stores (Packer et al., 2023; Zhong et al., 2024), and spoken history adds speech never meant for the assistant (Kim et al., 2025; Xie et al., 2026). Earlier agents named JARVIS orchestrate tools (Shen et al., 2023) or play Minecraft (Wang et al., 2023), but neither coordinates background work during a live conversation. 

## 8. Conclusion 

When an interactive model talks while a slow brain works in the background, each new turn can change what that work should do. Jarvis gives this coordination a brain of its own, in which models make the judgments and code checks each one against the latest state of every task. With the front model and back end held fixed, this change alone brings large gains on every benchmark and front model we tested, and the design carries over to vision with little change. We expect the same split to help assistants in glasses, cars and robots keep talking naturally while they act.

A.1. Jarvis-Audio Gate and binding. The LoRA adapter of the Native Gate has rank 8 and scale 16 and consists of 216 tensors. The routing pass builds its own prefix, and every pass that produces text or speech runs with the adapter switched off. The endpointing of the ASR observer uses an ensemble of three Silero VAD (Silero, 2024) instances and declares the end of an utterance after 1.1 s of silence. A DELEGATE 

event is bound to the most recent final transcript that started before the decision sample. Two adapter profiles share this design. A general profile serves daily use and all benchmarks, and a game profile serves sessions in which a game is explicitly connected. 

Decision requests. When JEV classifies a turn as a batch, a planner splits it into contiguous spans copied verbatim from the transcript, and each span is interpreted on its own. Every planned operation passes the same check as a JEV choice. Its action must be one that the runtime offers, a refinement or cancellation must name an existing task, and the version must still be live when it is applied. 

Ledger and workers. A task moves through eight states, and three of them, CANCELLED , SUPER-SEDED and FAILED , are terminal. When the only change since a worker planned is newly heard but unconfirmed speech, a bounded check asks whether that speech is related to the task, and the plan proceeds only on a clear “unrelated” with no further change during the check. Clearing the history writes a time fence into the ledger, so an asynchronous write that started before the reset cannot bring an old task back afterwards. A worker receives the objective, the relevant history and memory, the public policy and the tool schemas of the domain. A result names its task and version, a spoken answer, the supporting evidence and any artifacts, and a request for a missing detail moves the task to NEEDS_INPUT .

Memory on screen. Jarvis-Omni extends Memory with two layers. An in-match event memory records what happened during play, such as a kill, a suggestion or a correction, scoped to the user, the game, the match, the scene epoch and the round. Every event states whether it was observed, inferred or reported by the user, and whether it came from the screen or the microphone. Only an explicit correction from the user can supersede an event. ## B. Training the Native Gate 

All training of the Native Gate uses data we authored and synthesized ourselves. 

Scenarios. We wrote 264 Chinese and English scenarios (142 and 122) that cover what a voice assistant hears in daily use. They include everyday questions and small talk, lookups that need tools, requests to read memory, changes and cancellations of running tasks, background speech, remarks addressed to other people, and discussion of games versus requests to act in them. Each scenario has a label from a written rubric, DIRECT for 76, DELEGATE for 156 and LISTEN for 32, and a context of no game, a PvZ session or a voxel sandbox (160, 52 and 52). Later rounds added three kinds of material. Continuity scenarios cover 38 families of turns that only make sense with what came before, such as names, spelled identifiers, addresses, quantities, budgets and confirmations. Telephony 

variants pass the speech through 8 kHz resampling, G.711 𝜇 -law coding and colored noise at 15 dB and 9 dB. Conversational requests in 24 families, such as asking for a story, a joke, an explanation or some encouragement, teach the gate that a long answer is not the same as a task. ## C. Evaluation Protocol 

Benchmarks. The 278 regular 𝜏 -Voice tasks comprise 50 in airline, 114 in retail and 114 in telecom. FDB-v3 scores tool selection, argument accuracy, response quality and Pass@1, together with turn-taking behavior. For ContextDialog we fix 80 questions in advance, all four questions of 20 complete

conversations from both official splits. 

Front models and admission. MiniCPM-o 4.5 has no native function head, so a neutral controller admits requests after the final transcript. VoiceChat-11B has a native function head and a channel for tool results, and its own head decides when to call a tool. In every paired comparison the two harnesses share the same admission path. On Venus-Audio both use the trained Native Gate, and on the other two models both use the admission mechanism just described. Every harness uses a budget of 16,384 output tokens per task in addition to 12 tool rounds and 120 s. 

Simulated users and judges. All benchmarks run locally with their official task sets, tools, environ-ments and reward or scoring code. The simulated caller of 𝜏 -Voice is driven by DeepSeek-V4-Flash and voiced by Qwen3-TTS under the official policies, noise conditions and 200 ms tick, and the examiner of FDB-v2 combines DeepSeek-V4-Flash, Parakeet-TDT (NVIDIA, 2025) and Qwen3-TTS. Judges use the official prompts and rubrics. Every system we run meets the same callers, examiners and judges, and audio reaches it as real-time PCM. 

Baselines. QAA runs from its upstream code with its own gateway, task manager, backend runtime, announcements, cancellation and playback receipts. Our adapter supplies the duplex transport and a DeepSeek back end. Gander runs with its released weights, its lean orchestration mode and an official Whisper large-v3 recognizer, and a DeepSeek worker provider replaces its Codex back end with the same budget as the other harnesses. MoshiRAG runs on its native retrieval path. The official Venus harness runs with a DeepSeek executor.
