## 摘要
基于大语言模型的全双工语音服务允许用户在助手回应时说话。由于服务器生成输出并推进对话状态的速度可能快于客户端播放速度，后续用户语音可能基于用户从未听到的内容被理解。我们将这种失效称为生成式上下文错锚定（GCM）。为解决 GCM 问题，我们提出 PACE，这是一个与提供商无关的中间件层，将面向模型的上下文锚定到客户端回放边界——该边界是用户可能听到内容的系统可观测代理。在被打断后，PACE 会修复该上下文，排除从未到达回放阶段的助手内容，同时在异构语音运行时中保持低延迟生成。我们在基于浏览器的实时语音助手中端到端实现了 PACE 的仅音频投影路径，使用黑盒语音模型，且无需修改模型服务。我们还构建了 GCM-Bench，一个包含 108 个回放相对指称锚定案例的新型受控基准数据集。在 GCM-Bench 上，与仅取消基线相比，PACE 将指称锚定准确率从 25.0% 提高到 96.3%。在 200 个 Full-Duplex-Bench v1 打断样本上，它保持了打断响应质量。这些结果表明，将面向模型的上下文锚定在实际回放中是维持全双工语音对话一致性的实用方法。

## Abstract
LLM-based full-duplex voice services allow users to speak while the assistant is responding. Because servers can generate output and advance dialogue state faster than clients can play it, subsequent user speech may be interpreted based on content the user never heard. We call this failure Generative Context Mis-anchoring (GCM). To address GCM issues, we present PACE, a provider-independent middleware layer that anchors model-facing context to the client playback boundary, a system-observable proxy for what the user could have heard. After an interruption, PACE repairs this context to exclude assistant content that never reached playback, while preserving low-latency generation across heterogeneous voice runtimes. We implement PACE's audio-only projection path end to end in a browser-based realtime voice assistant using a black-box speech model, without modifying the model service. We also construct GCM-Bench, a new controlled benchmark dataset of 108 playback-relative referent-anchoring cases. On GCM-Bench, PACE raises Referent Anchoring Accuracy from 25.0% to 96.3% over a cancellation-only baseline. On 200 Full-Duplex-Bench v1 interruption samples, it preserves interruption response quality. These results show that grounding model-facing context in actual playback is a practical way to maintain consistency in full-duplex voice dialogue.

## 1. 论文的核心问题与整体含义

- **核心问题：生成式上下文错锚定（Generative Context Mis-anchoring, GCM）**  
  在全双工语音对话中，服务器生成助手语音并推进对话状态的速度，往往快于客户端实际播放语音的速度。因此，当用户打断助手并继续说话时，模型可能基于**用户从未听到的助手内容**来解释用户的新输入，导致指称错位、指令误解或错误执行动作。

- **研究动机与背景**  
  - 传统半双工语音交互轮流说话，系统可简单假设“助手说完后用户才说话”。  
  - 全双工语音交互允许用户随时打断、插话、澄清，但同时也引入了生成与播放之间的时间差。  
  - 现有工作多关注重叠语音建模、打断检测、端到端全双工模型或级联式控制器，但普遍忽略了“生成内容”与“实际播放内容”之间的**分布式一致性失败**。  
  - 现有打断机制（如仅取消生成、提供方截断接口）只能阻止进一步输出，不能修复已经推进的模型上下文。  

- **整体含义**  
  PACE 将“用户可能听到的内容”以**客户端回放边界**为代理，显式地对齐模型所见的对话上下文，从而在打断后修复模型状态，维持对话一致性。

## 2. 论文提出的方法论

### 2.1 核心思想

- PACE 是位于传输栈与模型运行时之间的**中间件层**，与具体 LLM、ASR、TTS 及传输协议无关。  
- 它通过**区分生成内容与播放落地内容**，维护一个**回合本地回放边界**，并在打断发生时据此裁剪或重注入上下文。  
- 设计原则包括：  
  - 生成与落地分离：流式生成保持低延迟，只有被客户端确认播放的内容才可视为“已落地”。  
  - 使用回合本地坐标：用 `turn_id` 而非全局样本计数，适应多传输、乱序和缓冲重置。  
  - 对运行时投影：根据后端能力选择文本历史重写、音频重注入或原生状态回滚。  
  - 门控不可逆动作：允许生成超前，但阻止未落地提案触发实际工具调用或交易。

### 2.2 关键状态对象与事件

- **OutputTurnLedger（输出回合台账）**  
  服务器端为每个助手响应回合维护一个条目 \( T_i \)，包含：  
  - `turn_id`：单调递增的回合标识；  
  - `audio_copy`：保留最近 \( W_{\max} \) 秒的发送音频副本；  
  - `text_copy`（可选）：响应文本内容；  
  - `semantic_spans`（可选）：音频区间 \([b_j, e_j]\) 及其语义角色（陈述、提案、问题、工具意图等）；  
  - `played_samples`：客户端已渲染的样本偏移，即**回放边界**；  
  - `state`：生命周期状态，如 generating → sent → playing → playback-complete，或 revoked。

- **PlaybackAck（播放确认）**  
  客户端周期上报：  
  \[
  A = \langle \text{audio\_turn\_id}, \text{played\_samples} \rangle
  \]  
  服务器据此维护当前回合的物理回放边界 \( B_p^i(n) \)。

### 2.3 回放边界与语义边界

- **物理播放边界** \( B_p^i(n) \)：表示第 \( i \) 回合中已渲染到扬声器的样本数 \( n \)。  
- **语义提交边界** \( B_s^i(n) \)（可选）：若存在可靠的对齐语义 span，则取满足 \( e_j + \epsilon \le n \) 的最后一个已完成 span 的音频终点；否则 \( B_s^i(n) = \bot \)。  
  \[
  B_s^i(n) = \max \left( \{ e_j \mid \text{finalized}(s_j) \land e_j + \epsilon \le n \} \cup \{0\} \right)
  \]  
  物理边界用于媒体撤销与音频重注入，语义边界用于更新规范文本历史或满足动作前置条件。

### 2.4 投影适配器

PACE 根据后端能力选择最强的投影方式：

- **级联式适配器**：对于 ASR–LLM–TTS 管线，通过重写文本历史实现。若没有可靠对齐，则移除不完整助手回合或使用音频重注入。  
- **音频重注入适配器**：适用于黑盒实时语音 API。流程为：  
  1. 从服务器端回合缓冲区中切出最近 \( L \) 秒已播放音频（\([n-Lf_p, n]\)）；  
  2. 将播放音频重采样至模型输入采样率，并拼接一个预合成的指令分隔音 \( P_{\text{delim}} \)（如“这是我打断前听到的内容。现在，以下是我想说的话：”）；  
  3. 将“已播放上下文 + 分隔音 + 用户打断后语音”依序注入模型输入缓冲。  
- **原生语音到语音适配器**：若后端提供对齐转录或语义 token 与检查点，则恢复到最近的兼容检查点；若完全黑盒，则只使用音频重注入，并将语义前置条件视为未落地。

### 2.5 打断处理流程

- **触发策略**：确认识别到真实打断或语义风险（未播放后缀包含提案/工具前置条件、用户话语包含指代短语等）时触发投影，避免短反语或误触发。  
- **在途取消**：  
  - 上游：发出 `response.cancel` 并置抑制标志，阻止剩余 delta 到达客户端；  
  - 下游：发送 Revoke 事件 \( R = \langle \text{audio\_turn\_id}, \text{after\_sample}, \text{reason} \rangle \)，客户端丢弃该边界之后尚未播放的音频。  
- **前向门控与顺序保证**：打断检测时同步关闭前向门，禁止新用户 tick 进入模型；先完成取消与注入，再释放被保持的用户 tick，确保输入顺序为：最后一个打断前 tick → cancel → 注入上下文 → 保持 tick → 新用户语音。

## 3. 实验设计

### 3.1 GCM-Bench 数据集

- **任务与指标**：回放相对指称锚定（playback-relative referent anchoring）。  
  - 主要指标：**指称锚定准确率（Referent Anchoring Accuracy, RAA）**，即模型在打断后的回应是否锚定在播放边界处的列表项，而非未播放的内部续项。  
  - 另报告 TOR（turn-obedience rate，是否有效响应）。  
  - RAA 计算公式：  
    \[
    \text{RAA} = \frac{1}{N_{\text{resp}}} \sum_{k=1}^{N_{\text{resp}}} \mathbb{1}[\hat{y}_k = \text{correct}]
    \]  
- **规模与构造**：  
  - 由 12 个列举场景 × 3 个打断延迟（12s / 16s / 20s）× 3 个指称操作（elaborate / next / repeat）全因子组合而成，共 **108 个样本**。  
  - 场景分为概念列表、过程列表、条件/准备列表三类。  
  - 用户输入轨迹由 TTS 合成，包含初始查询、指定延迟、打断话语和 15s 尾部静音；助手输出、网络传输、浏览器播放和修复过程在线执行，不模拟播放。  
- **评测流程**：流式执行 → 转录 → 用 GPT-5.5 自动评判。评判时提供打断前已播放文本、打断后回应、打断话语和操作类型，判断回应是否正确锚定。

### 3.2 Full-Duplex-Bench（FDB）兼容性研究

- 使用 **200 个官方 FDB v1 用户打断样本**进行独立兼容性与延迟评估。  
- 这些外部样本不用于计算 RAA，只评估普通话题切换打断下的响应质量、TOR 与延迟。  
- 指标包括 TOR、原始 0–5 LLM 质量分、打断到响应延迟。

### 3.3 对比方法

- **基线：仅取消（cancellation-only）**：取消当前生成并把打断后用户输入直接转发，不进行任何上下文修复。  
- **PACE（部署条件）**：额外使用客户端上报回放边界，从服务端回放缓冲区提取最近 5 秒已播放音频，配合指令分隔音 P1 注入。  
- **消融实验**：  
  - 3 种指令分隔音设计（P1 自然陈述、P2 直接切换、P3 包裹上下文）；  
  - 3 种回看窗口长度（2.5s、5s、10s）。

## 8. 缺点与局限性

- **样本规模与真实性有限**：GCM-Bench 仅包含 108 个样本，且用户轨迹由 TTS 合成，缺乏真实自然对话中的停顿、犹豫、噪音和口音变化，外部效度受限。
- **修复路径验证不完整**：论文只实现了音频重注入适配器，对语义提交边界、工具调用门控、跨提供商适配器、原生检查点回滚等能力均未进行端到端验证，研究结论尚不能推广到这些设计上。
- **单一模型与评判器**：主实验仅使用 DashScope Qwen-Audio-Realtime 一个黑盒实时语音模型，自动评判也仅依赖 ChatGPT 5.5，缺少多模型、多评判器的稳健性验证。
- **回看窗口的非单调效果**：10 s 回看窗口反而导致 RAA 显著下降至 65.74%，但论文对此现象缺乏深入机制解释，可能影响超参数选择的可迁移性。
- **next 操作评判偏差**：由于评判器无法获知未播放的续项，next 操作的基线准确率可能被高估，从而低估 PACE 的真实收益。
- **未与更强基线对比**：黑盒后端未暴露原生截断、文本重注入或状态回滚接口，因此无法确定 PACE 是否优于这些“如果可用”的替代方案，削弱了相对优势的证明。
- **延迟代价与工程复杂度**：打断路径平均增加 58.7 ms 延迟，且需要额外的 PlaybackAck 上报、服务端音频缓冲和投影逻辑，部署复杂度高于简单取消策略。

## 9. 总体评价与后续启示

- PACE 将全双工语音对话中的“生成内容超前于播放”问题形式化为 **生成式上下文错锚定（GCM）**，并提出以客户端回放边界为代理的轻量级上下文修复中间件，具有清晰的问题定义和较高的实用价值。
- 该方法不依赖具体模型或传输协议，能够在黑盒实时语音 API 上仅通过音频重注入实现，证明了修复路径的可行性与泛化潜力。
- 实验在自建 GCM-Bench 上取得 96.3% 的指称锚定准确率，并在外部 FDB v1 样本上保持质量不降，表明其对一般性打断场景也具有较好的兼容性。
- 后续工作应重点验证：语义级投影与工具调用门控、多提供商后端适配、真实用户对话下的鲁棒性、更自然的打断语料，以及如何在不增加过多延迟和复杂度的前提下维持分布式一致性。
- 总体而言，PACE 为全双工语音系统的上下文一致性维护提供了可复用的中间件范式，是该方向上一个有启发性且工程上可落地的贡献。
