## 摘要
我们提出 Qwen-Audio-Agent，这是一个通过前后台架构将全双工语音交互与异步任务执行相结合的框架。前端代理管理对话并在直接工具使用与委派之间进行选择，而后端代理在独立上下文中执行委派任务。编排运行时维护任务状态，协调用户输入和授权请求，并安排结果返回到对话中。该运行时将语音打断与任务取消、执行完成与结果交付分离，允许在委派工作继续的同时进行对话。环境事件和持久记忆在会话内及跨会话提供上下文。独立适配器支持与不同前端模型、后端代理和客户端集成。我们在桌面助手、智能座舱和语音客服中实例化了该架构。在一个包含 134 个案例的内部座舱基准上，混合执行实现了 91.04% 的任务成功率，而直接配置和全委派配置分别为 72.39% 和 80.60%。在匹配成功轮次的单独延迟评估中，混合执行相对于这些基线的平均任务执行延迟分别降低了 26.73% 和 30.91%。这些结果支持直接工具调用用于即时操作与后端委派用于多步任务的互补使用。

## Abstract
We present Qwen-Audio-Agent, a harness that combines full-duplex voice interaction with asynchronous task execution through a foreground-background architecture. A Frontend Agent manages dialogue and selects between direct tool use and delegation, while a Backend Agent carries out delegated tasks in a separate context. An Orchestration Runtime maintains task state, coordinates requests for user input and authorization, and schedules the return of results to the conversation. The runtime separates speech interruption from task cancellation and execution completion from result delivery, allowing conversation to continue while delegated work proceeds. Environmental events and persistent memory provide context within and across sessions. Independent adapters support integration with different frontend models, backend agents, and clients. We instantiate the architecture in desktop assistance, intelligent cockpits, and voice customer service. On an in-house cockpit benchmark of 134 cases, mixed execution achieves a task success rate of 91.04%, compared with 72.39% and 80.60% for the direct and all delegated configurations, respectively. In a separate latency evaluation on matched successful turns, mixed execution reduces mean task execution latency by 26.73% and 30.91% relative to these baselines, respectively. These results support the complementary use of direct tool calls for immediate operations and backend delegation for multi-step tasks.

## 1. 论文的核心问题与整体含义

- **研究动机**：语音代理需要处理跨越多轮对话的任务。用户可能在搜索进行中修改请求、在交易过程中补充约束、或询问仍在处理的文档。代理必须在响应新输入的同时保持任务状态。
- **关键难点**：全双工语音代理需要协调对话、任务执行和结果交付这三个不同时间尺度的活动。具体问题包括：
  - 打断语音响应不应隐式取消正在进行的任务；
  - 任务可能在用户说话时完成，结果需要保留到合适的对话时机；
  - 对话控制与任务执行需要分离，避免相互阻塞。
- **整体含义**：Qwen-Audio-Agent 被设计为一个“编排运行时/框架”（harness），作为连接模型、工具和执行环境的通用协调层。它允许用户继续对话，而之前的委派任务在后台异步执行，最终结果在合适时机回到对话中。

## 2. 论文提出的方法论

### 2.1 核心思想：前后台架构

- **Frontend Agent（前台代理）**：
  - 解释流式输入；
  - 维护全双工对话；
  - 在直接工具调用与后台委派之间做出选择。
- **Backend Agent（后台代理）**：
  - 在独立上下文中执行委派任务；
  - 拥有自己的工具和工作空间；
  - 可通过 ACP、A2A 或自定义接口替换（如 Qwen Code、Codex、Claude Code 等）。
- **Orchestration Runtime（编排运行时）**：
  - 维护任务状态；
  - 路由进度更新、用户输入和结果；
  - 协调语音打断、任务取消、结果交付等。
- **客户端**：捕捉输入、播放语音、显示产物、执行本地动作。

### 2.2 异步任务协调

- **委派入口**：通过 `spawn_thinking` 工具调用实现。前端提交一个**自包含目标**，其中包含约束和输入引用；对话历史和记忆不会自动传递给后台。
- **任务记录**：运行时创建任务记录并立即返回任务标识符，前端可继续对话。
- **任务生命周期**：包括 `queued`、`running`、`completed`、`failed`、`cancelled` 状态；前端可在后续轮次查询同一任务。
- **用户输入与授权**：后台可在执行中请求用户信息或授权；请求与原始任务关联，用户的回复被路由回对应任务。
- **语音打断 ≠ 任务取消**：打断语音只停止口语输出，任务执行状态保留；取消任务通过后端支持的控制接口另行转发。
- **执行完成 ≠ 结果交付**：完成的结果在用户说话或前端响应进行时被保留；同一收集窗口内的结果合并为一次响应请求；失败的交付可重试而不重复已完成的工作。

### 2.3 环境感知与统一事件

- 客户端提供视觉观察、应用或设备状态，使前端能基于当前环境解释后续请求。
- 环境状态变化采用**统一事件协议**，独立于前端提供商。每个事件类型定义：
  - 数据模式（schema）；
  - 保留规则；
  - 响应策略。
- 运行时验证事件后，可选择：直接处理、静默更新前端上下文、安排响应、或打断当前响应并请求新响应。

### 2.4 记忆与用户上下文

- 会话上下文由四部分构成：核心交互规则、助手画像、显式用户偏好、长期用户记忆。
- 默认记忆实现支持：
  - 对话中显式编辑；
  - 会话边界提取长期指令和稳定事实；
  - 可选学习过程：仅在跨会话一致证据支持下添加推断偏好。
- 优先级规则：
  - 当前用户请求 > 存储偏好；
  - 显式偏好 > 推断偏好；
  - 修订检查防止延迟的后台更新覆盖较新的修正；
  - 被用户拒绝的偏好不能再次自动添加。

## 3. 实验设计

### 3.1 数据集与场景

- **基准**：内部座舱基准，共 **134 个案例**：
  - 86 个短交互；
  - 48 个多步任务；
  - 总计 159 个用户轮次。
- 所有配置使用相同的 **41 个业务工具**、相同的初始状态和评估标准。

### 3.2 模型配置

- **前端代理**：Qwen Audio 3.0 Realtime Plus（音频）。
- **后端代理**：qwen3.8-max。
- **文本基线**：文本后端直接接收对应文本并执行工具。

### 3.3 对比方法（四种执行配置）

1. **Audio frontend, direct tools**：所有业务工具由前端直接调用。
2. **Audio frontend, all delegated**：所有业务工具调用均委派给后端。
3. **Text backend, direct tools**：纯文本后端直接执行工具（基线）。
4. **Audio frontend, mixed execution**：自适应选择直接执行或后台委派。

### 3.4 评估指标

- **能力评估**：结合 FDB V3 指标（Tool F1、参数准确率、任务成功率、回复质量）。
- **延迟评估**：在另一组所有配置均成功的 80 个轮次上测量（74 个短任务轮次 + 6 个多步任务轮次）。测量从语音请求结束（或文本提交）到任务完成，排除后续回复生成与播放。

## 6. 主要结论与发现

- **任务成功率**：混合执行达到 **91.04%**，为四种配置中最高；对比：
  - 直接前端执行：72.39%；
  - 全委派：80.60%；
  - 文本后端直接执行：90.30%。
- **分项表现**：
  - 直接执行在短任务上较强（86 个短案例中成功 83 个），但在多步任务上较弱（48 个中仅成功 14 个）；
  - 全委派将多步任务成功提升到 37 个，但短任务成功下降到 71 个；
  - 混合执行兼顾两者：短任务成功 84 个，多步任务成功 38 个。
- **延迟**：混合执行总体平均延迟最低，为 **4.729 秒**，相对直接前端执行降低 **26.73%**，相对全委派降低 **30.91%**；但在多步任务上，全委派和文本后端更快。
- **核心结论**：直接工具调用适合即时操作，后端委派适合多步任务，二者互补能同时提升任务成功率和总体延迟表现。
